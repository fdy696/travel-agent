# 行伴 Travel Agent 架构

## 1. 目标

行伴是一个面向 C 端用户的通用旅行 Agent。

当前 MVP 优先解决：

* 理解自然语言旅行需求
* 查询实时旅行信息
* 完成多步骤旅行研究
* 生成高质量完整旅行计划
* 支持连续对话与计划调整

当前阶段：

> **旅行计划的最佳表示是一份 Markdown。**

暂不把 Plan 建模成复杂业务实体。

---

## 2. 核心原则

### 2.1 Agent 负责不确定性

```text
LLM
→ 理解
→ 判断
→ 研究
→ 规划
→ 综合
→ 生成
```

### 2.2 Code 负责确定性

```text
Code
→ Tool 实现
→ API 调用
→ 权限
→ 参数校验
→ 错误处理
→ 安全边界
```

### 2.3 不把语义任务提前写成 Workflow

即使旅行规划通常存在：

```text
需求理解
→ Research
→ Plan
→ Output
```

也不代表需要固定执行图。

具体执行路径由 Main Agent 根据当前任务动态决定。

---

# 3. 总体架构

```text
                         User
                           │
                           ▼
                     Main Agent
                           │
          ┌────────────────┼────────────────┐
          │                │                │
          ▼                ▼                ▼
  Travel Planning       Tools        Travel Researcher
       Skill                              （按需）
                           │                │
                    search/weather         ├─ search
                       /maps               ├─ weather
                                           └─ maps
                                                │
                                                ▼
                                         Research Result
                                                │
                    ┌───────────────────────────┘
                    ▼
                  Main Agent
              Final Plan Synthesis
                    │
                    ▼
             Full Markdown Plan
                    │
                    ▼
                   User
```

Main Agent 始终是：

* 唯一用户对话入口
* 主要推理者
* 最终旅行方案拥有者
* 最终回答者

---

# 4. Main Agent

Main Agent 是通用旅行 Agent，不是单独的 Planning Agent。

负责：

* 普通旅行问答
* 理解用户需求
* 判断是否需要调用 Tool
* 判断是否需要委派 Researcher
* 综合用户上下文与研究结果
* 完成最终旅行方案
* 根据后续对话修改已有计划

例如：

```text
用户：
北京三日游，情侣，预算 3000

Main：
→ 理解需求
→ 必要时查询天气 / 地图 / 搜索
→ 必要时委派 Researcher
→ 综合信息
→ 输出完整 Markdown Plan
```

不额外拆：

```text
Plan Generator Agent
Plan Modify Agent
Plan Query Agent
Writer Agent
QA Agent
```

---

# 5. Travel Planning Skill

目录：

```text
skills/
└── travel-planning/
    └── SKILL.md
```

Skill 是旅行规划领域操作手册。

负责告诉 Main：

* 如何理解旅行需求
* 哪些约束最重要
* 什么时候需要补充信息
* 什么时候需要 Research
* 如何安排每日路线
* 如何考虑交通、预算、天气、营业时间
* 如何控制旅行节奏
* 完整计划应包含哪些内容
* Markdown 输出应该保持什么质量

Skill 定义：

```text
How to plan
```

而不是：

```text
固定执行流程
```

---

# 6. Tools

确定性的外部能力由 Tool 提供。

当前主要包括：

```text
search
weather
maps
```

Tool 负责：

```text
API 调用
实时数据
参数校验
错误处理
权限
确定性规则
```

模型负责判断：

> 是否需要调用 Tool，以及如何使用结果。

例如：

```text
天气事实
→ Weather Tool

地点距离 / 路线
→ Maps Tool

实时开放时间 / 预约规则
→ Search Tool
```

不让模型凭记忆猜实时事实。

---

# 7. Travel Researcher

Travel Researcher 是可选 SubAgent。

它的核心价值不是“专业分工”，而是：

> **隔离大量研究上下文。**

简单任务：

```text
Main
→ Tool
→ Main
→ Plan
```

复杂任务：

```text
Main
→ Travel Researcher
    ├─ 多次 search
    ├─ weather
    ├─ maps
    └─ 比较 / 核验
→ 返回简洁研究结果
→ Main 完成最终 Plan
```

适合委派的场景：

* 多城市路线
* 大量景点比较
* 复杂交通方案
* 预约规则较多
* 多来源信息核验
* 大量搜索会污染 Main Context

Researcher：

负责 Research。

不负责：

```text
最终旅行规划
用户对话
Plan 修改
最终 Markdown 输出
```

---

# 8. Final Plan Synthesis

最终旅行计划由 Main Agent 综合生成。

输入：

```text
Conversation
+
Travel Skill
+
Tool Results
+
Researcher Result（可选）
```

输出：

```text
Full Markdown Plan
```

例如：

```markdown
# 北京三日游

## 行程概览

## Day 1

### 上午

### 下午

### 晚上

### 交通

### 费用

### 提醒

## Day 2

...

## 住宿建议

## 美食建议

## 预算

## 出行准备
```

这里的关键定义是：

> **Main Agent 负责 Final Plan Synthesis。**

不是单纯充当 Markdown Writer。

当前 MVP 中：

```text
Travel Plan
=
Markdown Representation
```

未来出现真实结构化需求时，再拆分 Plan 与 Renderer。

---

# 9. Plan 修改

当前不实现 Patch / CRUD。

例如：

```text
用户：
第二天不要长城了，换成环球影城。
```

执行：

```text
当前 Conversation
+
已有 Plan
+
用户最新要求
        ↓
      Main
        ↓
重新综合受影响内容
        ↓
新的完整 Markdown Plan
```

Main 始终拥有完整计划语义。

---

# 10. Conversation State

使用 LangGraph / Deep Agents Checkpointer 保存线程状态。

主要保存：

```text
messages
tool calls
research result
plan markdown
conversation state
```

当前计划存在于 Conversation Context 中。

MVP 暂不建立独立 Plan 数据库。

---

# 11. Context Management

随着对话变长：

```text
旧消息
旧 Tool Result
旧 Plan 版本
```

可能造成 Context 膨胀。

优先使用 Runtime 自带的：

```text
Summarization
Context Compression
SubAgent Isolation
```

如果实际 Eval 证明长期 Plan 修改不稳定，再增加轻量：

```text
current_plan.md
```

或：

```text
current_plan_markdown
```

作为 Agent Working Snapshot。

它仍然不是正式 Plan Entity。

---

# 12. Runtime

推荐：

```text
Deep Agents
+
LangGraph Runtime
```

负责：

* Agent Loop
* Tool Calling
* SubAgent Delegation
* Checkpoint
* Context Summarization
* Skill Loading
* Streaming
* Human-in-the-loop（未来）

Runtime 不承载旅行领域业务逻辑。

---

# 13. Streaming

前端流式展示 Agent 状态，例如：

```text
正在理解旅行需求
正在查询实时信息
正在研究交通方案
正在整理行程
```

不暴露模型内部 Chain of Thought。

最终仍由 Main 输出完整 Plan。

---

# 14. Evals

质量控制优先通过 Evals，而不是堆 Validator Agent。

建议建立旅行任务测试集：

```text
短途旅行
多城市旅行
情侣旅行
亲子旅行
老人旅行
自驾
预算变化
天气变化
计划修改
复杂 Research
```

核心指标：

```text
需求满足度
路线合理性
实时信息准确性
预算一致性
完整性
Tool 使用合理性
Research 必要性
延迟
成本
```

只有 Eval 证明存在稳定问题时，再增加 Rubric 等运行时检查。

# 18. 最终架构原则

```text
Main Agent
→ 理解、决策、规划、最终综合

Travel Skill
→ 旅行规划方法论

Tools
→ 实时、确定性的现实能力

Travel Researcher
→ 高噪声复杂研究的上下文隔离

Runtime
→ 状态、上下文、委派、流式与持久化

Markdown
→ 当前旅行计划的最佳表示
```

最终原则：

> **Agent 负责决策，Skill 负责方法，Tool 负责事实，SubAgent 负责隔离，Runtime 负责连续性。**

> **Main Agent 拥有最终旅行方案的语义，并负责 Final Plan Synthesis。**

> **先让 Agent 把旅行计划做好，再让真实业务需求决定系统需要增加什么复杂度。**
