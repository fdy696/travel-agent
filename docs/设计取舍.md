可以把你的意思专业化成下面这句，面试里很好用：

**“我的设计原则是：确定性的业务能力由系统和代码控制，非确定性的认知能力交给模型。也就是业务规则、状态流转、权限、版本、事务这类可验证的逻辑由程序兜底；意图理解、信息提取、研究、生成、自然语言修改这类需要语义判断的能力交给 LLM。”**

再精炼一点，可以说：

> **确定性归代码，概率性归模型；业务边界由系统定义，模型在边界内发挥能力。**

这个版本很适合架构面试。

如果面试官继续问“为什么”，可以展开成：

> LLM 本质上是概率模型，擅长处理模糊语义和开放性问题，但不应该承担版本号、状态机、事务、权限这类需要百分之百确定的系统职责。所以我会把系统拆成两层：业务系统负责约束和事实，模型负责理解、推理和生成。这样既利用模型能力，又不会把核心业务正确性押在模型输出上。

结合你的旅游 Agent，可以直接举例：

> 比如用户说“第一天到了以后我只想休息”，理解这句话会影响哪些行程，是模型擅长的；但修改后覆盖哪一份当前计划、`plan_id` 是否保持不变、`updated_at` 由谁更新、是否只允许修改自己的计划，这些必须由 Repository 和代码决定，而不能让模型自己算。

再往架构层次提高一点，可以说：

> **LLM 是决策参与者，不是业务事实源。Domain Layer 才是业务事实源。**

或者：

> **Agent 负责 semantic decision，Workflow/Domain Service 负责 deterministic execution。**

这两句拿来解释你现在的架构尤其合适：

```text
Main Agent / Intelligence
负责：
意图理解
需求抽取
Research

格式修复（Schema Parse 失败时）

        ↓

Workflow / Repository / Domain
负责：
状态推进

```

如果让我选一句最适合面试现场背下来，我会用：

> **“我会把系统边界设计成：模糊的语义决策交给模型，确定性的业务规则交给代码。LLM 可以决定‘怎么理解、怎么生成’，但不能决定‘系统事实是什么’。”**

这比“让业务控制业务，模型控制模型”专业得多，也准确表达了你现在这套架构真正的设计思想。



我的一个核心设计原则是：**业务系统负责定义边界和事实，模型负责在边界内发挥认知和生成能力。**

具体来说，我不会要求模型所有阶段都统一输出 JSON，也不会为了“结构化”而结构化，而是根据这个输出后续由谁消费来决定数据形态。

比如在旅游 Agent 里，用户需求会影响后续 Workflow 的状态判断、需求合并和流程推进。像目的地、天数、人数、预算这类信息，后面的程序需要直接读取和判断，所以我会要求模型输出结构化 JSON，并通过 Pydantic 做 Schema 约束。

例如：

```json
{
  "destinations": ["洛阳"],
  "duration_days": 2,
  "traveler_count": 2,
  "budget_level": "舒适型"
}
```

这里 JSON 的目的不是限制模型，而是因为这些数据本质上属于业务状态，需要机器稳定消费。

但 Research 阶段不一样。

Research 的目标是尽可能完整地收集和组织信息，例如景点开放时间、天气、交通、预约要求、风险、工具调用失败，以及“为什么某个景点应该安排在第二天”这种上下文关系。

这类信息天然是开放的、信息密度很高。如果强制模型压缩成一个固定 JSON Schema，很容易因为 Schema 表达能力不足而丢失细节。

所以 Research Agent 我更倾向让模型直接输出 Markdown：

```text
洛阳博物馆周一闭馆，因此 8 月 10 日无法安排，
应该放到第二天周二。

龙门石窟 8 月天气炎热，建议上午游览，
既能避开高温，也能减少暑期人流影响。

公交路线查询工具失败，因此交通方案使用搜索结果补充。
```

这时候 Markdown 不是因为“文本比较好看”，而是因为这部分本质上属于知识上下文，主要消费者仍然是后面的 LLM，而不是业务代码。

到了最终 Plan，我会再根据产品需要选择 Rich JSON。

因为 Plan 后续需要版本管理、修改、持久化以及前端展示，所以它仍然应该是机器可理解的业务实体；但 Schema 必须足够丰富，比如允许 description、reason、tips、booking_notes 等字段，避免为了结构化牺牲模型的信息表达能力。

所以我的原则不是“JSON 比 Markdown 好”或者“Markdown 比 JSON 好”，而是：

**如果下游消费者是程序，就优先结构化；如果下游消费者主要是模型，就保留高信息密度的自然语言；如果既要给程序操作，又要保留模型表达能力，就设计 Rich Structured Schema。**

再往底层总结，就是：

**确定性的业务事实交给代码，概率性的语义能力交给模型；数据格式由消费方决定，而不是由模型框架决定。**

比如模型可以理解用户说“第一天到了以后我只想休息”意味着应该调整哪些活动，但它不能决定当前计划的 `plan_id`、归属和覆盖写；这些必须由 Repository 决定。修改直接覆盖 current_plan，不保留历史版本——用户不需要也不应该感知版本号。

所以我会把 LLM 看成一个 semantic decision engine，而不是 system of record。模型负责理解、研究和生成，Domain Layer 负责状态、版本、事务和业务事实。


我不会统一要求模型输出 JSON，而是根据下游消费者决定数据形态：程序要消费的业务状态用 JSON，模型要继续消费的知识上下文用 Markdown，既要程序操作又要保留表达能力的领域对象用 Rich JSON。底层原则是，模型负责语义决策，代码负责系统事实。”

这句话基本就把你现在这套设计讲明白了，而且不是那种“LLM + JSON + Workflow”关键词炖汤式回答。


这句话可以作为项目的核心设计原则，建议放进 docs/设计取舍.md：

数据形态由下游消费者决定，而不是统一要求模型输出 JSON：程序要消费的业务状态使用 JSON；模型还要继续消费的知识上下文使用 Markdown；既需要程序操作、又要保留表达能力的领域对象使用 Rich JSON。底层原则是：模型负责语义决策，代码负责系统事实。

对应当前架构：

数据	形态	原因
TravelRequirements	普通 JSON	Workflow 要累计、判断
Research Report	Markdown/Text	后续模型仍需阅读完整研究上下文
PlanDraft / PlanDocument	Rich JSON	需要持久化、修改和程序访问
用户展示结果	Markdown	Renderer 负责视图生成
这也解释了为什么高德路线不能完全交给模型“记忆或推理”：

路线事实由高德工具返回；
模型决定何时调用路线工具、如何把结果纳入计划；
代码负责 API 调用、错误处理、计划覆盖保存和字段一致性；
Renderer 负责把最终 Rich Plan 展示给用户。
可以再压缩成一句架构口号：

模型做语义，代码守事实；状态用 JSON，知识用 Markdown，领域对象用 Rich JSON。
