下面这版按我们刚刚收敛后的方案写，重点是：**先把旅行规划做好，不急着把一份 Markdown 养成企业级业务实体。**

# 行伴 Travel Agent 架构

## 1. 目标

行伴是一个面向 C 端用户的通用旅行 Agent。

当前 MVP 优先解决：

* 自然语言理解旅行需求
* 查询实时旅行信息
* 完成多步骤旅行研究
* 生成高质量完整旅行计划
* 支持连续对话和计划调整

当前阶段，**旅行计划就是一份 Markdown 内容**。

暂不处理 Plan CRUD、版本、结构化存储等问题。

---

## 2. 核心原则

> 模糊、概率性的语义决策交给模型；确定性的能力和边界交给代码。

进一步：

```text
LLM
→ 理解、判断、研究、规划、生成

Code
→ Tool 实现、权限、外部 API、确定性规则

Skill
→ 告诉 Agent 如何完成旅行规划

SubAgent
→ 隔离复杂、高噪声研究任务
```

不因为任务存在：

```text
需求 → Research → Plan → Output
```

就把它写成固定 Workflow。

具体执行路径由 Agent 动态决定。

---

## 3. 总体架构

```text
                         User
                          │
                          ▼
                   Main Deep Agent
                          │
            ┌─────────────┼─────────────┐
            │             │             │
            ▼             ▼             ▼
     Travel Planning    Tools      Travel Researcher
          Skill                     （按需）
                          │             │
                    search/weather     ├─ search
                    maps/...           ├─ weather
                                      └─ maps
                                            │
                                            ▼
                                     简洁研究结果
                                            │
                     ┌──────────────────────┘
                     ▼
                 Main Agent
                     │
                     ▼
            Full Markdown Plan
                     │
                     ▼
                    User
```

Main Agent 始终是用户唯一的对话入口和最终回答者。

---

## 4. Main Agent

Main Agent 是通用 Agent，不是专门的 Planning Agent。

负责：

* 普通旅行问答
* 理解用户需求
* 判断是否需要调用工具
* 判断是否需要委派 Researcher
* 综合用户信息和研究结果
* 生成完整旅行计划
* 根据后续对话修改已有计划

例如：

```text
用户：
北京三日游，情侣，预算3000

Main：
→ 理解需求
→ 查询天气
→ 必要时 Research
→ 生成完整 Markdown
```

不需要：

```text
Plan Generator Agent
Plan Query Agent
Plan Modify Agent
QA Agent
```

---

## 5. Travel Planning Skill

`skills/travel-planning/SKILL.md`

Skill 是旅行规划的领域操作手册。

负责告诉 Main：

* 如何理解旅行需求
* 哪些信息比较重要
* 什么时候需要补充信息
* 什么时候值得进行 Research
* 如何安排每日路线
* 如何考虑天气、交通、预算、营业时间
* 完整旅行计划应该包含什么

例如最终 Markdown：

```text
# 北京三日游

## 行程概览

## Day 1
- 上午
- 下午
- 晚上
- 交通
- 费用
- 提醒

## Day 2
...

## Day 3
...

## 住宿建议

## 美食推荐

## 预算

## 出行准备
```

Skill 定义规划质量，不实现固定 Workflow。

---

## 6. Tools

确定性的外部能力由 Tool 提供：

```text
search
weather
maps
...
```

Tool 负责：

```text
API 调用
参数校验
错误处理
权限
确定性数据获取
```

模型只决定：

> 现在是否需要调用这个 Tool，以及如何使用结果。

例如天气必须来自 Weather Tool，而不是让模型猜。

---

## 7. Travel Researcher

Researcher 是可选 SubAgent。

不是每次规划都调用。

简单任务：

```text
Main
→ weather
→ search
→ 直接生成 Plan
```

复杂任务：

```text
Main
→ Travel Researcher
    ├─ 多次 search
    ├─ weather
    ├─ maps
    └─ 交叉整理
→ 返回简洁结果
→ Main生成 Plan
```

适合 Researcher 的场景：

* 多城市旅行
* 景点很多
* 预约规则复杂
* 交通方案很多
* 需要大量搜索和比较

Researcher 的价值主要是：

> **隔离大量搜索上下文，避免污染 Main Agent。**

Researcher 最终只返回一段简洁结果。

不需要定义正式的 `ResearchBrief` Schema，也不保存。

---

## 8. 旅行计划生成

当前版本不再设计：

```text
PlanContent
PlanDraft
PlanDocument
create_plan
update_plan
Renderer
Plan Repository
```

旅行计划直接由 Main 生成 Markdown：

```text
Conversation
     +
Travel Skill
     +
Tool Results
     +
Researcher Result（可选）
     ↓
Main LLM
     ↓
Full Markdown Plan
```

这份 Markdown 就是当前计划。

用户继续说：

```text
加入798艺术区
```

Main 根据当前上下文中的旅行计划重新生成修改后的完整 Markdown。

当前不做 Patch / CRUD。

---

## 9. 完成质量

普通问答不需要额外检查。

完整旅行规划任务可以使用一个很薄的、任务级质量检查，例如 Deep Agents `RubricMiddleware`：

```text
Main生成最终回答
        ↓
是否真的是完整 Plan？
   ├─ Yes → END
   └─ No  → Main继续完善
```

只检查语义质量，例如：

* 是否真的给出了完整计划
* 是否只输出了摘要
* 是否覆盖用户最新要求
* 是否遗漏主要部分

不把它发展成 Validator / Repair Workflow。

如果实际运行证明 Skill 已经足够稳定，这层甚至可以关闭。

---

## 10. Conversation State

Redis / LangGraph Checkpointer 继续保存对话线程：

```text
User
Main
Tools
Researcher结果
Plan Markdown
后续修改
```

因此当前计划可以直接存在 conversation context 中。

当前阶段不额外建立 Plan 数据库。

---

## 11. 当前明确不做

MVP 暂不引入：

```text
❌ Planning Graph
❌ 固定 Workflow
❌ Plan Generator Agent
❌ Plan CRUD
❌ Plan 数据库
❌ PlanContent / PlanDocument
❌ Renderer
❌ Validator / Repair Agent
❌ Delivery Middleware
❌ 两套 Stream
❌ 正式 ResearchBrief 对象
```

没有真实需求之前，不提前建设这些能力。

---

## 12. 什么时候再升级

未来出现以下需求，再引入结构化 Plan：

```text
跨会话长期保存
跨设备查看
多人共享
Plan 版本历史
订单 / 酒店 / 机票绑定
结构化搜索
行程协作
```

届时可以演进为：

```text
Markdown Plan
      ↓
Structured Plan
      ↓
Persistence / Versioning
```

如果未来任务扩大到：

```text
几十个城市
大量并行研究
签证 / 航班 / 酒店分别独立处理
复杂依赖关系
```

再考虑 Workflow / 多 SubAgent orchestration。

---

## 13. 最终架构原则

```text
Main Agent
→ 大脑

Travel Skill
→ 旅行规划知识

Tools
→ 确定性能力

Travel Researcher
→ 复杂研究的上下文隔离

Markdown
→ 当前旅行计划
```

最终原则：

> **先让 Agent 把旅行计划做好，再把真正出现的业务复杂度交给系统。**

> **不要为了未来可能存在的问题，提前把一次旅行规划变成一套工作流平台。**

这版比上一版又砍掉了一层，适合作为当前 MVP 的基准架构。
